# Security Review — Ollama LLM Provider Delta

Reviewer: system2:security-sentinel
Date: 2026-07-20
Trigger: `bin/ardconfig-onboard` diff touches `check_aws_credentials` and adds a parallel `check_ollama_available` (credential/prereq-check pattern match).

## Scope of Review

Reviewed the **current on-disk state** (not just the diff) of:

- `bin/ardconfig-onboard` — `resolve_llm_provider()`, `ensure_ai_deps()`, `check_aws_credentials()` (unchanged), `check_ollama_available()` (new), `invoke_agent()`, `main()` dispatch
- `agent/onboard_agent.py` — `create_agent()` provider branching, `SYSTEM_PROMPT`, `parse_agent_output()`
- `conf/ardconfig.conf` — new `ARDCONFIG_LLM_PROVIDER`/`ARDCONFIG_OLLAMA_HOST`/`ARDCONFIG_OLLAMA_MODEL` defaults
- `README.md` — user-facing prereq/config documentation
- `tests/bin/fixtures/mock_ollama_server.py`, `tests/bin/fixtures/fake_venv/bin/{python,pip}` — test-only harness code (not shipped)
- `tests/bin/test_ardconfig_onboard.bats`, `tests/agent/test_create_agent.py`, `tests/agent/test_nfr8_scope_boundary.py` — verification coverage for the above

Read but confirmed **unchanged / out of this delta's scope** (`agent/tools.py`, `lib/common.sh`, `lib/output.sh`) — cited only as context for the threat model, not as findings requiring remediation here.

Verification method: this review is evidence-based, not just source-reading. I ran:
- The full `pytest tests/agent` suite (13/13 pass) and `bats tests/bin` suite (15/15 pass) against the real on-disk code.
- A standalone injection-harness (`/tmp/.../pwn_test.sh`) that fed 5 classic shell/Python-breakout payloads (`$(...)`, backticks, `"; cmd; #`, Python-string-breakout, and a heredoc-terminator-collision payload) through the exact `ARDCONFIG_OLLAMA_HOST="$host" ... python - <<'PYEOF'` construct used in `check_ollama_available()`. None achieved code execution; all five were observed by the inner Python process as inert string data via `os.environ`.
- A contrast test of the pre-existing (unchanged) `check_aws_credentials()` python `-c` string-interpolation pattern with a single-quote-breakout payload, confirmed it **is** a real injection-shaped construct (see Findings, informational, out of scope).
- pip requirement-specifier parsing of `ollama>=0.4.8,<1.0.0` to confirm correct bounds and single-argv-element passing (no word-splitting).
- `os.path` traversal probes against `agent/tools.py`'s `read_file`/`write_file` guards (pre-existing, unchanged, informational only).

## Data Classification

| Data | Touched by this delta? | Classification |
|---|---|---|
| AWS credentials (via `boto3`/`aws configure`/env vars) | No — `check_aws_credentials()` path is byte-identical and only reached when `ARDCONFIG_LLM_PROVIDER=bedrock` | Secret |
| Ollama server host/model config (`ARDCONFIG_OLLAMA_HOST`, `ARDCONFIG_OLLAMA_MODEL`) | Yes — new | Low-sensitivity config (local dev tool, no inherent secret) |
| USB vendor/product IDs, board name, USB model string | Yes — sent to whichever LLM backend is selected (Bedrock or Ollama) as prompt content | Low-sensitivity device metadata (not PII/PHI) |
| Board profile JSON (fqbn, core, USB IDs, etc.) written to `profiles/` | Yes — generated by either backend | Non-sensitive, repo-local config |
| No usernames, emails, tokens, session identifiers, or health data are touched anywhere in this delta. | — | N/A |

There is no PII/PHI in this data flow. Ollama, by default, has no authentication — so anything sent to `ARDCONFIG_OLLAMA_HOST` (prompt text: vendor/product IDs, board name, USB descriptor strings) is not encrypted-in-transit-by-default and not access-controlled at the receiving end, unlike the Bedrock path which requires authenticated, TLS-protected AWS API calls. See Findings (Informational-1) for the doc-risk angle on this.

## Threat Model

**Assets:**
- The developer's local machine / shell (already fully trusted/controlled by the user in this tool's model)
- `profiles/*.json` (board definitions consumed by `ardconfig-setup`/`ardconfig-verify`)
- `/etc/udev/rules.d/99-arduino.rules` (written via `sudo cp` in `update_udev_rules()`, unchanged by this delta)
- AWS credentials (bedrock path only, unchanged)
- Prompt content sent to whichever LLM backend is active (USB metadata, board name — low sensitivity)

**Actors:**
- The legitimate local developer (primary/only expected actor — this is a single-user local CLI, not a multi-tenant service)
- A malicious/compromised dependency in the venv (`strands-agents`, `boto3`, `ollama` PyPI packages) — supply-chain actor
- A malicious or manipulated LLM response (either Bedrock's Claude or a local Ollama model) attempting to drive the agent's tool calls outside intended bounds — prompt-injection-adjacent actor, mitigated by `agent/tools.py`'s allowlists (unchanged by this delta)
- A local process listening on `ARDCONFIG_OLLAMA_HOST` that is not actually Ollama (e.g., if the user points the tool at a stale/wrong port) — low-severity, self-inflicted misconfiguration risk

**Attack surfaces introduced by this delta:**
1. `ARDCONFIG_OLLAMA_HOST`/`ARDCONFIG_OLLAMA_MODEL` env/config values flowing into a Python heredoc (`check_ollama_available()`) — verified injection-safe (see Findings).
2. `ARDCONFIG_OLLAMA_HOST` flowing into `ollama.Client(host=...)` / `OllamaModel(host=..., ...)` — an outbound HTTP destination now controllable via config, defaulting to `localhost` but not restricted to it.
3. New JIT pip install of `ollama>=0.4.8,<1.0.0` — same trust model as pre-existing `strands-agents`/`boto3` JIT installs (supply-chain risk, not new in kind, only in the specific package name).
4. Documentation/UX surface: default backend now an unauthenticated local server instead of an authenticated cloud API — a "silent trust downgrade" risk if a user later repoints `ARDCONFIG_OLLAMA_HOST` without realizing the security-model implications.

This is a **local, single-user developer CLI**. There is no multi-tenant boundary, no network-facing service, and the acting user already has full shell access to their own machine. Per the review brief, findings are calibrated accordingly — theoretical risks that require an already-fully-compromised local attacker to matter are not flagged as actionable findings.

## Abuse Cases

1. **Malicious `ARDCONFIG_OLLAMA_HOST` value attempts shell/Python code injection via the prereq-check heredoc.** Tested empirically (5 payload classes including a heredoc-terminator-collision attempt); all failed to execute. See Findings.
2. **User (or a script acting on the user's behalf) sets `ARDCONFIG_OLLAMA_HOST` to a non-localhost address without realizing prompt content (USB vendor/product IDs, board name strings) will now be sent, unauthenticated and typically unencrypted, to that remote host.** No code-level vulnerability, but a real doc/UX gap. See Findings (Informational-1).
3. **A compromised or typo'd PyPI package name is installed via `ensure_ai_deps()`'s JIT pip install** (e.g., if `ollama` were ever typo-squatted or if the pin were malformed). Verified the actual pin (`ollama>=0.4.8,<1.0.0`) parses correctly as a single, properly-bounded requirement — not an unpinned/wildcard install. See Findings.
4. **A malicious or low-quality local Ollama model returns a board profile JSON, or an out-of-allowlist tool-call attempt, designed to make the agent write outside `profiles/` or run an arbitrary `arduino-cli`/shell command.** Mitigated entirely by the pre-existing, unchanged `agent/tools.py` guardrails (`write_file` confined to `profiles/`, `arduino_cli_search` prefix allowlist with `shell=False` list-form `subprocess.run`, `run_setup`/`run_verify` fixed-script invocation). Confirmed byte-identical via the new `NFR-8` golden-hash test (`tests/agent/test_nfr8_scope_boundary.py`), which is a strong, durable control against silent re-introduction of a broader tool surface alongside future provider changes.
5. **A user copy-pastes the `ollama pull <model>` guidance string from an error message into their shell**, where `<model>` is `ARDCONFIG_OLLAMA_MODEL` (attacker would need to already control the user's own env/config to weaponize this — self-injection, not a real attack path for this tool's threat model). Noted as a theoretical curiosity only; not a finding.
6. **Empty-string env var precedence bug** (now fixed in this delta, verified by dedicated tests): previously `os.environ.get(KEY, default)` treated a present-but-empty env var (arising from `conf/ardconfig.conf`'s `ARDCONFIG_BEDROCK_MODEL="${ARDCONFIG_BEDROCK_MODEL:-}"` pass-through) as "set", silently using `""` instead of the intended default model/region. Not an injection or confidentiality issue, but a correctness/availability concern that could have caused confusing failures; now covered by `test_precedence_fix_*` tests.

## Vulnerability Checklist

### Authn/Authz
- No new authn/authz boundary is introduced. Bedrock path continues to rely on AWS SDK credential resolution (unchanged). Ollama has no authentication by default — this is inherent to Ollama's design, not a defect in this delta, but is a real trust-model difference from Bedrock (see Informational-1).
- No privilege escalation path found: `sudo` usage (`update_udev_rules()`) is unchanged and unrelated to the LLM-provider selection.

### Input validation and injection (including prompt injection)
- `ARDCONFIG_LLM_PROVIDER` is validated against an explicit allowlist (`bedrock|ollama`) before any downstream use, both at the bash layer (`resolve_llm_provider()`) and defensively again in Python (`create_agent()`'s `else: raise ValueError`). Good defense-in-depth.
- `ARDCONFIG_OLLAMA_HOST`/`ARDCONFIG_OLLAMA_MODEL` reach a subprocess boundary (`check_ollama_available()`'s heredoc, `invoke_agent()`'s python -m invocation) exclusively via the `VAR="$value" command` env-var-prefix bash idiom, read back inside Python via `os.environ`, never string-interpolated into shell or Python source text. **Verified empirically injection-safe** (see Findings).
- Prompt-injection surface (LLM tool-calling) is unchanged by this delta — `agent/tools.py` and `SYSTEM_PROMPT` are confirmed byte-identical via golden-hash tests. The only change is *which* model drives that same constrained tool loop.
- Pre-existing (unrelated to this delta, not fixed here) — `check_aws_credentials()` interpolates `${region}` directly into a Python `-c` string literal (`region_name='${region}'`). Confirmed via harness that a region value containing a single quote can break out of the string and inject arbitrary Python. Out of scope for required fixes (file unchanged), flagged as informational context.

### Secrets handling
- No new secret-bearing values are introduced. AWS credential handling path is untouched. Ollama has no credential of its own to mishandle.
- No secrets are logged: `output_step`/`output_result` only emit status strings and the (non-secret) host/model config values a user already set themselves.

### Logging/telemetry privacy
- All error/status messages route through `output_step`, which JSON-encodes values via `jq --arg` (confirmed by reading `lib/output.sh`) — a malicious/malformed `host` value cannot break the JSON output schema.
- `check_ollama_available()`'s heredoc discards Python stderr (`2>/dev/null`), which slightly reduces operator debuggability but has no privacy implication (no sensitive data would have been in that stream anyway).
- No new telemetry/analytics/network-call-home behavior is introduced by this delta.

### Dependency risk
- New runtime dependency: `ollama` PyPI package, pinned `>=0.4.8,<1.0.0`. Verified this parses as a correctly bounded requirement (not unpinned, not a stray extra package) and is passed to pip as a single argv element (no word-splitting risk even though quoting is already correct).
- Same JIT-install trust model as the pre-existing `strands-agents`/`boto3` dependencies: `ensure_ai_deps()` runs `pip install` against whatever index `pip` is configured to use, with no `--require-hashes`/lockfile pinning. This is a pre-existing pattern in the codebase, not newly introduced — noted under Defense-in-Depth, not a required fix.

### Supply chain/build pipeline
- No CI/build pipeline changes in this delta. `pyproject.toml`/`requirements-dev.txt` additions are test-only (`pytest>=8.0,<10`), not shipped to end users.
- Test fixtures (`tests/bin/fixtures/fake_venv/bin/{python,pip}`) are inert stand-ins gated by an explicit `ARDCONFIG_TEST_FIXTURE_MODE` env var with a hard-fail default case (unrecognized mode exits 1 with an error) — they cannot silently activate outside the test harness.

## Findings

### Finding 1 — Informational: Env-var-prefix heredoc pattern in `check_ollama_available()` is genuinely injection-safe as implemented
- **Severity:** Informational (positive finding / confirms the design doc's claim)
- **Evidence:** `bin/ardconfig-onboard:107-161`. Empirically tested 5 payload classes (command substitution, backticks, quote-breakout, Python-string-breakout, heredoc-terminator-collision) against the exact construct via a standalone harness reproducing `ARDCONFIG_OLLAMA_HOST="$host" ARDCONFIG_OLLAMA_MODEL="$model" python - <<'PYEOF' ... PYEOF`. All payloads were observed inertly as string data (`os.environ["ARDCONFIG_OLLAMA_HOST"]`); none achieved shell or Python code execution. This holds because (a) the heredoc delimiter `PYEOF` is quoted, so the shell performs zero expansion inside the heredoc body and the body's text is fixed at parse time from the script source, not from `$host`'s runtime value — even a payload containing a literal `PYEOF` line cannot terminate the heredoc early; and (b) `VAR="$host" cmd` is a plain bash parameter expansion assigned to an env var, which is not re-scanned by the shell for further expansion (unlike `eval`).
- **Remediation:** None required — confirming this design choice is correctly implemented, not just intended.

### Finding 2 — Informational: `ARDCONFIG_OLLAMA_HOST` is an unvalidated outbound destination (acceptable for this tool's model, but should be paired with the doc note in Finding 3)
- **Severity:** Informational
- **Evidence:** `agent/onboard_agent.py:78-80` (`OllamaModel(host=host, ...)`), `bin/ardconfig-onboard:109,128` (`ollama.Client(host=host)`). No allowlist/validation is applied to `host` beyond it being a string.
- **Assessment:** For a local, single-user CLI where the operator already fully controls their own shell/env, this is not an actionable "SSRF" vulnerability in the traditional sense (no privilege boundary is crossed — the same user who could set `ARDCONFIG_OLLAMA_HOST` could equally run `curl` directly against any host). Appropriately out of scope for a code-level fix.
- **Remediation:** None required at the code level. See Finding 3 for the associated documentation gap, which is the actionable half of this concern.

### Finding 3 — Low: No inline warning when `ARDCONFIG_OLLAMA_HOST` is set to a non-localhost address
- **Severity:** Low
- **Evidence:** `README.md` (lines ~93, 115, 255) documents the new default and the `ARDCONFIG_OLLAMA_HOST`/`ARDCONFIG_OLLAMA_MODEL` config vars, but nowhere states that prompt content (USB vendor/product IDs, board name, USB descriptor strings) will be sent to `ARDCONFIG_OLLAMA_HOST` **unauthenticated** if it is repointed away from `localhost`, nor that this differs from the Bedrock path's authenticated/TLS-protected behavior. `check_ollama_available()` and `create_agent()` also emit no runtime warning in this case (e.g., `output_step warn` when `host` is not `localhost`/`127.0.0.1`).
- **Remediation (recommended, not blocking):** Add one sentence to the README's Ollama prerequisites bullet, e.g.: "If you set `ARDCONFIG_OLLAMA_HOST` to a non-local address, board metadata (USB IDs, board name) will be sent to that server; Ollama has no authentication by default, so only point this at a server you trust." Optionally, emit a one-time `output_step warn` in `check_ollama_available()` when `host` does not start with `http://localhost`/`http://127.0.0.1`. Low severity because the data involved is non-sensitive USB metadata, not credentials or personal data, and the user is the one setting the value.

### Finding 4 — Informational: JIT-installed `ollama` package version pin verified correct
- **Severity:** Informational
- **Evidence:** `bin/ardconfig-onboard:83` — `missing+=("ollama>=0.4.8,<1.0.0")`. Verified via pip's own requirement parser that this resolves to `ollama` with specifiers `>=0.4.8` and `<1.0.0` (a proper bounded range, not unpinned/wildcard), and verified via a bash array probe that it is passed to `pip install` as a single, correctly-quoted argv element (no word-splitting on the embedded `>`/`<`/`,` characters — none of those are `IFS` characters, and the value contains no whitespace regardless).
- **Remediation:** None required.

### Finding 5 — Informational: Bedrock credential-check path confirmed byte-identical (no regression, no new secret mishandling)
- **Severity:** Informational
- **Evidence:** `git diff HEAD -- bin/ardconfig-onboard` shows `check_aws_credentials()`'s body (lines 96-105 in current file) is untouched; only its call site became conditional (`if [[ "$ARDCONFIG_LLM_PROVIDER" == "bedrock" ]]; then check_aws_credentials ... fi`), confirmed via `git show HEAD:bin/ardconfig-onboard` diff against current state showing zero changes inside the function body. Ollama has no credential of its own, so there is no new secret-adjacent value to mishandle on the new path.
- **Remediation:** None required.

### Finding 6 — Informational (out of delta scope): Pre-existing string-interpolation injection shape in `check_aws_credentials()`
- **Severity:** Informational / not a required fix (unchanged file, outside this delta's change set — flagged only because the review brief asked to confirm this path's byte-identical status, and the contrast with the new Ollama code's safer pattern is instructive)
- **Evidence:** `bin/ardconfig-onboard:99` — `"${venv}/bin/python" -c "import boto3; boto3.client('sts', region_name='${region}').get_caller_identity()"`. Harness-tested: a `region` value containing a single quote followed by Python syntax (e.g. `us-west-2'); import os; os.system('...'); print('`) breaks out of the Python string literal and is parsed as executable Python source (confirmed via `python3 -c` with the interpolated string; failed only on `ModuleNotFoundError: boto3` in the sandboxed test environment, not on syntax — the injected `os.system(...)` call was successfully parsed into the executed statement sequence). `ARDCONFIG_AWS_REGION` is a config/env value the same local user controls, so this is not an actionable cross-privilege vulnerability under this tool's threat model, and it predates and is untouched by this delta.
- **Remediation:** Not required for this delta (file unchanged, out of scope). Recommended as a follow-up catalog entry: migrate `check_aws_credentials()` to the same env-var-prefix + `os.environ` pattern that `check_ollama_available()` correctly demonstrates, for consistency and defense-in-depth (not because a real exploit path exists today).

## Required Fixes Before Ship

**None.** No Critical or High severity findings were identified in this delta. All findings above are Informational or Low, and none block shipping.

## Defense-in-Depth Recommendations

1. Add the non-localhost trust-boundary note to `README.md` and/or a runtime `output_step warn` for non-local `ARDCONFIG_OLLAMA_HOST` values (Finding 3). Low cost, closes the one real doc gap found.
2. Consider migrating `check_aws_credentials()` to the same `os.environ`-based pattern used in `check_ollama_available()`, purely for consistency/hygiene — not urgent, not part of this delta (Finding 6).
3. Consider capturing (not discarding) the Python heredoc's stderr in `check_ollama_available()` behind a `--verbose`/debug flag, to aid operator troubleshooting of unreachable-server cases without regressing the current clean JSON-step UX.
4. If a lockfile/hash-pinning mechanism is ever introduced for the JIT-installed AI dependencies (`strands-agents`, `boto3`, `ollama`), extend it uniformly rather than special-casing `ollama` — this is a pre-existing gap across all three, not new to this delta.
5. Keep the `NFR-8` golden-hash scope-boundary test (`tests/agent/test_nfr8_scope_boundary.py`) in place and treat any future need to regenerate it as a signal requiring explicit security review — it is currently the strongest structural control keeping "add a new LLM provider" changes from silently widening the agent's tool surface.

## Residual Risk + Monitoring Plan

**Residual risk:** Low overall. The delta's only genuinely new attack surface (env-controlled host/model values reaching a subprocess boundary) was verified injection-safe both by design and by empirical testing. The one real residual risk is a documentation/awareness gap (Finding 3): a user who repoints `ARDCONFIG_OLLAMA_HOST` to a remote, unauthenticated host will send low-sensitivity USB/board metadata there with no in-tool warning. This does not rise above Low severity given the non-sensitive nature of the data and the fact that the user is the one making that configuration change.

**Monitoring / follow-up:**
- No runtime monitoring is applicable — this is a local CLI with no telemetry pipeline.
- Recommend the doc fix (Finding 3) be picked up as a small follow-up task; no gate should block on it.
- If `ARDCONFIG_OLLAMA_HOST`/`ARDCONFIG_OLLAMA_MODEL` validation or warnings are added later, extend `tests/bin/test_ardconfig_onboard.bats` accordingly (existing test scaffolding — mock Ollama server, fake venv — is already well-suited to cover it).
- Re-run this review if `agent/tools.py` or `SYSTEM_PROMPT` ever change (the `NFR-8` golden-hash tests will fail first and should trigger that re-review automatically per the delegation map's security-pattern trigger).
